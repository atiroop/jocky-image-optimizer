# Architecture

## Current foundation

- `jocky-image-optimizer.php`: WordPress plugin header, guarded entry point, Composer autoload, lifecycle hooks, and deferred bootstrap.
- `src/Plugin.php`: lifecycle and admin-only composition root.
- `src/Admin/AdminPages.php`: capability-gated Dashboard and Settings pages, Settings API registration, and escaped diagnostics output.
- `src/Settings.php`: centralized defaults and deterministic input validation.
- `src/Delivery/FrontendDelivery.php`: default-off WordPress image filters and a narrowly scoped Elementor Image/Image Box adapter, preserving original `<img>` markup as the fallback.
- `src/Delivery/DerivativeResolver.php`: bounded registry lookup and source, lifecycle, path, MIME, size, and device/inode/size/mtime identity checks; no full-file hashing or writes on frontend requests.
- `src/Delivery/DeliveryCache.php`: invokes WP Rocket's documented `rocket_clean_domain()` API when present and displays manual external-cache purge guidance.
- `src/CapabilityDetector.php`: checks loaded PHP libraries and their format support, and searches PATH for known encoder executables without invoking them.
- `src/Optimization/OptimizationManager.php`: explicit-only orchestration for JPEG/PNG inputs, bounded validation, separate outputs, no-benefit handling, and measured results.
- `src/Optimization/*Encoder.php`: lossless `jpegtran`/`oxipng` and lossy MozJPEG/`pngquant` command adapters. Binary resolution accepts only known IDs and trusted configured paths.
- `src/Optimization/CwebpEncoder.php` and `AvifEncoder.php`: explicit JPEG/PNG-to-still-WebP/AVIF conversion using bounded argv execution, configurable quality/mode, and separate outputs. AVIF uses at most two threads and configurable speed.
- `src/System/ProcessRunner.php`: argv-array process execution with shell bypass, bounded output capture, timeout, and a restricted inherited environment. Windows uses private temporary capture files because process pipes can block despite nonblocking mode; Linux uses drained pipes.
- `src/Optimization/ImageValidator.php`: bounded streaming PNG chunk/order/CRC validation, JPEG marker/dimension validation, RIFF WebP chunk/dimension/alpha validation, bounded ISO-BMFF AVIF box/dimension checks, and animation detection.
- `scripts/package.php`: creates a WordPress-installable ZIP with a `jocky-image-optimizer/` root and includes Composer's production autoloader.
- `tests/integration/PluginIntegrationTest.php`: exercises the packaged plugin against the WordPress PHPUnit runtime, including lifecycle, admin pages, settings, diagnostics, and media fixture preservation.
- `bin/install-wp-tests.sh`: pinned WP-CLI scaffold installer for an isolated WordPress core and test library; it must use a disposable database and temporary paths.

Milestone 3 verification: GitHub Actions run [42735752617](https://github.com/atiroop/jocky-image-optimizer/actions/runs/42735752617) passed on PHP 8.3, including actual cwebp/avifenc conversions, independent dwebp/avifdec decoding, and the packaged-plugin WordPress 6.6.11/7.1.4 matrix. The run caught a WebP RIFF-size offset defect that was fixed before the passing run. It confirms behavior in the CI runner only; production PHP-FPM paths, binaries, policies, and resource limits still require environment-specific checks. See `VALIDATION.md` for the actual measurements and full limitations.

The application has no third-party PHP runtime dependencies. Composer provides PSR-4 autoload metadata. Deployment/package creation runs Composer first and ships `vendor/` so WordPress does not need Composer.

## Safety boundaries

The explicit engine API writes only a separate destination beneath configured roots. Staging uses a private mode-0700 temporary directory; after validation, the engine promotes the file with same-filesystem hard-link creation that does not replace an existing path. Filesystems without hard links fail closed. This assumes the configured managed roots and their parent directories are trusted and not writable by hostile local users; PHP has no portable openat-style directory-handle API to eliminate all path replacement races. Activation preserves existing settings.

## Milestone 4 queue and media flow

`QueueSchema` installs versioned `{prefix}jio_jobs` and `{prefix}jio_worker_slots` InnoDB tables with `dbDelta`; normal bootstrap verifies required tables/indexes and repairs missing scanner/worker seed rows before recording the current schema version. The current schema version 3 adds nullable derivative file identity additively while retaining existing records. A stale version, missing table/index, or missing slot triggers an idempotent retry. Queue claims and worker/scanner leases use single conditional InnoDB `UPDATE ... ORDER BY ... LIMIT 1` statements plus random ownership tokens; the atomic update both selects and claims one available row without an explicit transaction. Deactivation preserves tables, jobs, and derivatives.

`MediaIntegration` exposes a Media Library row action and optionally listens to `wp_generate_attachment_metadata` only to enqueue after core generates sizes; it returns the input metadata unchanged. `AttachmentTargetProvider` uses attachment APIs and current upload-root checks to accept local JPEG/PNG originals and registered sizes. `AttachmentProcessor` reuses the existing optimizer and writes separate deterministic `.jio.*` destinations. Derivatives are registered with source and output integrity metadata and remain separately stored.

## Milestone 5 recovery and lifecycle

Schema version 3 extends the existing idempotent `dbDelta` migration with derivative ownership, recovery audit, cleanup-batch tables, and nullable lightweight delivery identity. The derivative registry stores upload-relative source/output paths, attachment and variant IDs, MIME/format, byte counts, source fingerprint and SHA-256, derivative SHA-256, a hash of the core attachment references, encoder identity/parameters, and validation/lifecycle timestamps. Existing `_jio_derivative_*` metadata is imported only when the current WordPress source relationship and exact expected JIO destination agree; this establishes an initial digest but cannot prove that legacy bytes were never modified before the first import.

Integrity reads stream in 1 MiB chunks. Each file is capped at 50 MiB and each service operation budgets at most 100 MiB of aggregate reads. Keyset pages cap per-attachment verification at ten records and bulk UI listings at ten rows. Work exceeding these limits is deferred or marked as a conflict and never becomes deletable based on a partial hash. No full-library scan or hash runs on frontend requests. The bounded legacy scanner advances through attachment IDs. Destructive cleanup has a backend fail-closed gate: it is unavailable unless `JIO_ENABLE_DESTRUCTIVE_RECOVERY` is explicitly true and WordPress environment type is `local` or `development`. Admin handlers, WP-CLI cleanup/start/run, scheduled worker execution, and `RecoveryService` all enforce the gate; preview and verification remain available. This local/development-only opt-in is for disposable validation, not production operation.

When the gate is enabled, cleanup reads only database-registered records, confines canonical paths to the current uploads root, rejects symlinks, rechecks the current attachment and core metadata, registry ownership and digest, active queue work, source/derivative identity, and confirms the candidate is not any current WordPress-managed original or thumbnail path immediately before unlink. A per-attachment MySQL advisory lock is shared with optimization; bulk batches also have a batch lock, persistent keyset progress, and at most ten records per invocation. These checks reduce races but cannot synchronize WordPress core metadata changes, attachment deletion, or external backup restore. Portable PHP cannot eliminate the final unlink TOCTOU window against a hostile local writer. The plugin does not install a core deletion hook because WordPress does not allow this plugin lock to veto or serialize core deletion; the default-off gate is the safety control. The uploads tree must be writable only by trusted site processes. A failed post-unlink registry transition is reported as a conflict and the row is marked conflicted when the database permits; the file is already absent, so operator review may still be needed. Failed audit or batch-state writes are surfaced rather than reported as successful completion.

This is a derivative recovery system, not an original-file backup. Optimization creates separate output paths and does not overwrite original source bytes. “Restore original delivery state” verifies the WordPress reference; it cannot restore missing bytes. UpdraftPlus or another verified backup is required for original-byte or whole-site recovery. Preview/verification can import trusted legacy JIO metadata and write registry/audit status, but do not delete files. Cleanup is denied by default in production and staging; the explicit constant/environment gate restricts destructive execution to local/development tests. In that gated path, it removes one exact derivative only after all current checks succeed. The plugin lock is connection-scoped and does not synchronize external WordPress or backup tools. Any filesystem race after the final identity check is a documented limitation, not a guarantee PHP can eliminate. The implementation assumes the uploads tree and parents are writable only by trusted site processes, refuses symlink paths, and fails closed when identities change. Files larger than the hashing cap need operator inspection.

`BulkScanner` uses an attachment-ID cursor and bounded pages, with a dedicated slot preventing overlapping scans. Progress snapshots normalize legacy or partial option values to all fields consumed by `assets/admin.js` (`status`, `scanned`, `total_images`, and `jobs_added`). The worker handles one job per cron tick, and WP-CLI accepts batches up to ten. WP-Cron depends on site traffic; operators can schedule `wp jio worker run --batch-size=10` externally. The plugin does not install cron or run a daemon. Direct uncached SQL is required for transactional queue claims; values are prepared and table identifiers come from the trusted `$wpdb->prefix`.

The optimization resolver assumes local files under the active site's upload base directory. Filtered/offloaded storage is refused. Multisite uses the current site's `wp_upload_dir()` root but has not been tested in a multisite suite. Portable PHP cannot eliminate every filesystem TOCTOU race when parent directories are writable by hostile local users. Cancellation affects pending jobs only. If metadata persistence fails after a valid derivative is written, the retry will not overwrite that derivative; operator cleanup may be needed.

## Milestone 6 frontend delivery

The frontend module runs only on normal frontend rendering and is disabled unless the saved `frontend_delivery` setting is explicitly true. It filters `wp_get_attachment_image` (Media Library APIs, featured images, and core renderers that use the API) and `wp_content_img_tag` (core-recognized attachment images in Classic/Gutenberg-rendered content). A `<picture>` wraps only the parsed IMG tag, preserving surrounding links/captions and original `img` attributes, responsive srcset/sizes, and universal fallback. AVIF/WebP source lists use same-attachment, same-aspect candidates. Elementor Image and Image Box can sanitize the earlier WordPress image-filter output; the optional `elementor/widget/render_content` adapter therefore runs after widget rendering, checks the widget's selected attachment ID and WordPress image URL, then reuses the same identity-checked renderer on only the matching `<img>` token. This hook is registered harmlessly when Elementor is absent. CSS/background delivery remains unsupported and must retain its original URL. Elementor Element Caching is an explicit compatibility limit: its document-level cache can skip this hook. The adapter checks Elementor 4.4.0's persisted cache setting and returns unchanged widget HTML whenever Element Cache is active. No supported targeted runtime invalidation API is documented; the public files manager clear method is a site-wide files/data purge, not used automatically. Administrators must disable Element Cache and run Elementor's Clear Files & Data action to remove stale cached markup. Previously cached JIO output from an older build requires this manual purge before relying on Delivery OFF.

The derivative table migration adds nullable `derivative_identity` without rewriting existing records. New optimizer outputs record `dev:ino:size:mtime`; requests compare it to `stat()` without hashing content. Legacy rows with null identity, active queue work, changed source/attachment metadata, unrecognized format, path mismatch, missing or symlinked path, wrong MIME/size, or resolver exceptions fail back to original markup. Registry lookups are memoized per request and capped at 80 distinct attachments. Existing legacy derivatives are not automatically imported or hashed on page views; regenerate through the normal optimizer before delivery. The database identity cannot eliminate hostile-writer TOCTOU races, and external caches may serve stale HTML or references after files are removed outside the plugin lifecycle.

Settings changes and the first successful derivative registration in a worker request call `rocket_clean_domain()` when the documented function exists; this is a whole-domain purge, not a targeted purge. A notice requests manual Cloudflare/other cache purge. No CDN API calls or User-Agent cache variation are used. Disabling affects uncached requests immediately; purge external caches to revoke already-cached markup.

## Planned processing boundary

The current orchestration and adapters intentionally remain separate from WordPress media handling. PNG validation verifies every chunk CRC and basic ordering/critical-chunk rules, but actual IDAT decompression validation is delegated to the selected encoder. JPEG marker parsing does not itself decode entropy-coded scan data; encoders must fully decode input and output validation is supplemented by their exit status and structural checks. Process timeouts terminate the direct child process; portable PHP does not provide a cross-platform process-tree kill primitive, so the adapter set is restricted to known encoders that do not launch persistent child workers. Lossy adapters reject metadata-preserving requests; `jpegtran` and `oxipng` request metadata retention and compare detected metadata categories after encoding, not exact metadata bytes. Quality values are encoder-specific and not directly comparable. Storage, backup, job persistence, and delivery concerns remain separate from encoder implementations.

## Deployment notes

Cross-format conversion requires `cwebp` or `avifenc` on the PHP process PATH (not required for activation). AVIF defaults to speed 6 and at most two threads; lossy AVIF keeps alpha at lossless quality. The request accepts quality 1–100 and passes it to cwebp quality. The adapter detects libavif version and uses `--qcolor`/`--qalpha` on 1.2+, or maps to `--min`/`--max` quantizers and lossless alpha on earlier releases. Encoder quality scales are not directly comparable. Conversion rejects EXIF-bearing sources because orientation cannot be guaranteed. Other detected metadata requires opt-out and may be stripped. Output dimension/format/alpha checks are structural; runtime does not compare rendered pixels or exact color appearance. Independent decoding is part of the encoder integration test, not a runtime dependency. Animated formats are rejected. The PHP process must have access to the target uploads filesystem and required libraries. Linux binary paths, executable permissions, PHP-FPM PATH, memory limits, and process restrictions can differ from CLI and from Windows. Verify diagnostics as the actual web/PHP-FPM user. Do not auto-install system packages or auto-configure cron.

## Integration testing

GitHub Actions runs production ZIP validation and installs that ZIP into temporary WordPress cores for integration tests against WordPress 6.6.11 and 7.1.4 with PHP 8.3 and MySQL 8.0. The test package is required from the isolated `WP_PLUGIN_DIR`; the Composer loader prioritizes that copy so tests cannot silently exercise the checkout source. Local tests use the same pinned installer script, a temporary core/test-library directory, and a disposable database.
